\subsection{Frontend Technologies}

In order to utilise the World Wide Web that he had invented in 1990, Tim Berners-Lee had created WorldWideWeb, later Nexus~\cite{NEXUS}, the first web browser - which served as an inspiration for many subsequent browsers. These browsers were designed to load HyperText Markup Language (HTML) files, which later evolved into different web pages for consumer use as the Web had developed. Combined with Cascading Style Sheets (CSS) and JavaScript, they form the base framework used to create webpages ever since the dawn of the internet - with HTML files serving as the base, CSS files beautifying the styles, and JavaScript adding functionality to the webpages.

While it is possible to design a website solely with these three technologies, over time many different code libraries have emerged, bringing different controls and code reusability to web development. Ultimately, these libraries would be merged together and form a framework - with the intention of helping users create websites from start to end, as well as handling authentication, routing among other key features~\cite{FRAMEWORKS}. Three of the most popular JavaScript based frameworks include: React, Angular and Vue.js, though there are many others written in different programming languages.

When it comes to the differences between the three of them, there are some notable differences. For starters, Angular is known to have a steeper learning curve - given that it uses TypeScript as opposed to JavaScript, along with the extensive features that it provides. React has an easier learning curve as it revolves around the idea of reusable components, while Vue is the easiest to learn - given that the syntax is similar to HTML. Alongside this, Vue and React are best used for smaller applications, while Angular is the first choice for large enterprise applications~\cite{FRAMEWORKS_COMPARE}. 

However, for the frontend of this project I will be using a combination of Next.JS with TailwindCSS. Next.js is based on the React framework, and is designed to overcome React's limitation when it comes to server-side rendering, whilst including many of its own additional features~\cite{DB_NEXTJS} such as better Search-Engine Optimisation and Routing, both of which would be required for the web application to gain traction in the future.

\subsection {Backend Technologies}

Similarly to the frontend, there are a number of backend frameworks in existence that are widely used for different web applications. These frameworks are designed to act as the core of any client-server based system, as they process majority of the application logic, and facilitate communication with database systems. Many of these frameworks are widely used, including - but not limited to Node.js and Spring Boot.

Node.js is based on JavaScript, and is known for its high performance and scalability. It is an event-drive runtime environment designed to build scalable network applications, where callbacks are triggered for each connection. Unfortunately, these features can also be seen as disadvantages of the system, wherein the code for callbacks can be increasingly difficult to manage in complex applications - while the event-driven architecture won't be beneficial for tasks that may be more CPU-intensive~\cite{BACKEND_FRAMEWORKS_BLOG}~\cite{BACKEND_FRAMEWORKS_REPORT}~\cite{SPRING}.

Spring Boot is part of the Spring framework, and is known for its security and integration capabilities. It uses a three-tiered architecture which include layers acting as Controllers, Services and Data Repositories - forming microservices as part of the overall backend system. Compared with Node.js, Spring Boot would be more preferable for security with the many libraries that it uses for it, as well as the fact that it has a larger support community - allowing for ease of development during this project~\cite{SPRING}. Furthermore, the benefit of Spring Boot will be that it will allow for seamless integration with the database system required - allowing me to focus on developing the endpoints required for the product. As a result I have chosen to use this framework for backend development.

\subsection {Database Management Systems}

There are two major types of databases that are widely used across different applications, SQL and NoSQL. SQL (Structured Query Languages) have been the most popular form of storing data since the beginning of web application history, and this is largely due to the durability factor. This stems from the ACID properties that relational databases follow - which ensures that database transactions are full, and that data is kept intact and consistent. NoSQL databases on the other hand do not follow the idea of having a relational structure. These are typically customized to fit the needs of a particular application, and it is unlikely that one example of a NoSQL database can be used for many different types of applications~\cite{SQL_COMPARE}.

The biggest difference that NoSQL databases have in common is the use of BASE properties over ACID. BASE (Basically Available, Soft state with Eventual consistency) has been a critical discussion point when the two types of databases have been compared in the past - and are typically used in applications where inconsistent data can be tolerated~\cite{SQL}. This is not the case for my application - especially given that user details are required to be stored securely, so it is imperative that I make use of a database system that follows ACID properties.

There are still many databases to choose from that follow ACID properties. Two of the biggest database management systems include PostgreSQL and MySQL - which appear very similar on the surface however there are some key differences which make them stand out from each other. The biggest is that PostgreSQL is an Object-Relational Database Management System, providing the facilities of a standard Relational DBMS with additional Object Oriented concepts. This is beneficial for integration with Spring Boot, as it allows me to define entities that can be translated to database tables - allowing me to manipulate the system via the use of the Repository level in the backend. As a result, I have opted to use PostgreSQL to serve as my database.

\subsection{Controller-Service-Repository Pattern}

Usage of Spring Boot for the backend has helped introduce a pattern similar to a Model-View-Controller Pattern. This is done by grouping the individual components into separate packages: Controller, Service and Repository; each of which have their own roles when it comes to organising the code.

The Controller is used to receive the RestAPI endpoint request. This does not contain much logic - rather it instead acts as a protective layer to separate the external endpoint and the core application logic, as well as builds the final ResponseEntity to be sent back to the frontend. 

The Service is where the core application logic is kept. Given that it is not directly exposed to external sources, it is safer to handle business logic and processing requests here - as this is what will be accessing the repositories used to perform operations on the system's database.  

The Repository is used as the bridge between the backend and the database. Any entities that have been saved to the repository are translated into a record for the database table that the repository represents. At the same time, these repository classes can have different types of functions designed specifically to retrieve certain pieces of data from the database, to then use in the service layer.

\subsection{Client-Server Architecture}

Client/Server Architecture relates to the idea that two separate applications communicate with each other as part of a wider product. The Client would ask for and receive services that the Server would provide~\cite{CSA}. This is the case in my product, wherein the backend is responsible for managing any information that is to be stored and retrieved from the database, and the frontend requests this for for the end user to interact with.\\

Communication is facilitated through the use of API endpoints. These endpoints are URLs within a web application which point towards the different functionalities that an application provides. On the server side of the connection, the server would process the information required, whereas the requests for each function are called on the client side~\cite{API}.\\

An example of how this is setup in my application can be with how we view the list of qualifications that the user sees when they sign up to the application. \subsection{Security Detail}

Being a web application that handles a user's private data, is is imperative that I secure the product, by minimising possible weaknesses that can be exploited. Out of all software available, the web browser is one that will run code provided from untrusted sources whenever presented\cite{WEB_SEC} despite being used to submit and receive private information across the world. With that in mind, it was important that I research adequate methods to protect the JSON Web Token that it used to prove the user's authenticity.\\

There are many ways that people may choose to store JWTs, be it in memory or even in the browser's session storage. However, research has shown that these are not as viable compared to the use of cookies. Storing the token in memory leaves the risk of it disappearing when the browser is closed or reset. On the other hand, storing it in Session Storage leaves the token vulnerable to Cross-Site Scripting (XSS) attacks. With cookies, by settings the HTTPOnly, Secure and SameSite flags to be true - there is added protection which prevents these cookies from ebing identified by external JavaScript, protecting them from XSS attacks~\cite{JWT}.

This is not the only point of concern when it comes to security. It is also crucial to sanitise inputs as a means of removing any possible control characters - so as to not inject any malicious code into the system. This is a benefit of React, and therefore Next.JS, as all inputs are sanitised before being used within the frontend application. This is achieved by converting everything to a string before being rendered or used, adding further prevention to XSS attacks~\cite{XSS_REACT}. Where SQL injections are concerned, there are two types of queries that have been written for the backend. \subsection{Privacy}

The United Kingdom has a General Data Protection Regulation Act that has been imposed to set out the legislation behind usage of personal data in a variety of applications. The following principles are set out in the act~\cite{GDPR}:

\begin{itemize}[label=-]
	\item Lawfulness, Fairness and Transparency - Refers to the idea that businesses and organisations must be open about how they use data, and that it should only be used for necessary or legitimate reasons.
	\item Purpose Limitation - Should not be used more than it has been collected for.
	\item Data Minimisation - Should only be limited to what is required for the intended purpose
	\item Accuracy - Should be kept accurate and up to date
	\item Storage Limitation - Should be stored for as long as have been required
	\item Integrity and Confidentiality - Data must be kept secure, and protected against unauthorized misuse or amendments.
	\item Accountability - Organisations are required to comply with the other principles of the act.
\end{itemize}

To authenticate, the password input is encoded, and the hashes are then compared against each other before authentication is granted to the user.

	@PostMapping("/login")

\section{Refresh Tokens}

The tokens used to verify the user's authenticity have been designed to expire after 15 minutes, for situations where the token is stolen by an attacker. However, users will want to utilise the system for a period longer than 15 minutes - so to accommodate I have introduced a Refresh Token system. This I have achieved with the introduction of middleware. 

The middleware will take the tokenExpiry cookie that was previously generated when the user logs in, as shown in Section 3.2. This cookie contains a timestamp that represents two minutes before the token cookie itself is due to expire. The middleware will check to see if the time is within those two minutes, and if that is the case it will send an API request to generate a new token. The token is generated and sent back to the middleware, where it's converted to a cookie and then sent with the original request response to the frontend.

\begin{lstlisting}[language=JavaScript, caption={If we have entered that expiry window, then the request is sent for a new token. The values are then unpacked and converted to cookies for the next response to the frontend.}]
	// middleware.ts
	const isExpired = checkExpiration(tokenExpiry);
	// time is up?
	if (isExpired) {
		console.log("Token Expired!")
		const token = req.cookies.get("token")?.value;
		await axios.post('http://localhost:8080/api/refresh/refresh-token', {},{
			headers: {
				'Cookie': `token=${token}`,
				
			},
			withCredentials: true}).then((resp) => {
			// Apply new values to the cookies
			const newToken = resp.data.token;
			const newExpiry = resp.data.tokenExpiry;
			// Calculate cookie expiry time
			const cookieExpiry = Number(newExpiry) + 120;
			const newExpiryDate = new Date(0).setUTCSeconds(cookieExpiry);
			// Apply to new cookies
			response.cookies.set("token", newToken, {expires:newExpiryDate, httpOnly:true, secure:true, sameSite:"strict"});
			response.cookies.set("tokenExpiry", newExpiry, {expires:newExpiryDate, httpOnly:true, secure:true, sameSite:"strict"});
			console.log("Token Refreshed!");
		});
	}
\end{lstlisting}
In the backend, the API request will gets the user from the database and check to see if they have a valid refresh token. It is unlikely that they won't have one - given that a valid one would generate when they log in should one be expired - however if this is not the case then they would have a new one generated. After this, with the refresh token confirmed - a new JWT is generated using the user's username as the payload.
\begin{lstlisting}[language=Java, caption={The backend checks if the token is valid, before generating a new JWT}]
	// RefreshTokenService.java
	public AuthenticationResponseDto refreshToken(String accessToken) {
		User user = userService.getUserByUsername(jwtService.extractUsernameFromToken(accessToken));
		// Checks expiry data is valid.
		if (hasInvalidRefreshToken(user))
		// No token found? Somehow? Brand new one then
		createToken(user);
		
		final var newAccessToken = jwtService.generateToken(user.getUsername());
		return new AuthenticationResponseDto(newAccessToken);
	}
\end{lstlisting}

\section{Methodology}
There are many different approaches when it comes to Software Development. The Waterfall model for example focuses on completing phases of the project at a time, i.e. requirements first, then design and implementation etc. For me this approach is very strict - as it requires myself as the developer to consider the application as a whole from the very beginning, when the requirements of the product are continuously evolving as development ensues. Another example of a development approach can be Rapid Application Development. This approach focuses more on developing components in parallel to each other, prioritizing speed over completion of features. Though it closely aligns with my current development approach - it is also unsuitable as it requires components to be integrated to the system as a later date, as opposed to during the development process.\\

As a result, I have chosen to develop this application by following a combination of the Agile and Incremental Approaches. The Incremental Approach allows me to focus on developing one feature at a time - ensuring that it's working to the fullest before I move my focus onto the next feature in sequence. The Agile Approach here relates to the flexibility that I am giving myself; there is no dedicated client for this product, so I am able to develop features at my own pace and alternate between different features as I wish to. At the same time, I am then able to revisit features if I am required to make any additions following its completion - given the ongoing flexibility in requirements. This can be referred to as similar vertical slicing - wherein the application is developed component by component - and ultimately expands from these components as a dependency.

\section{Requirements Analysis}

The Requirements Analysis is an ongoing phase - changing if required as the product evolves. Following this approach leaves me with the flexibility to revisit components if I am required to add a feature which I had not have included in the first place, unaware at the time of it's use. Despite that, this application has been an idea for several months, and I had drafted a design for how the questions could be presented to students.
