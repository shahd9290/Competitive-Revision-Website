\section{Objective}
This project aims to facilitate revision for the average student, whilst also capitalizing on their competitive nature.  From working in education, I have observed how some children love to be competitive with each other when there is a reward promised at the end of a certain competition - to the extent that they may try to find a way to cheat the system. Though cheating is discouraged, it gave me the idea to encourage competition in a way that benefits the student when it comes to their revision. I aim to achieve this by adopting a points system inspired by the Picarats seen in the Professor Layton video game series~\cite{LAYTON} - where students will lose marks each time they fail to answer a question correctly until a set minimum. This can be enhanced by hosting regular contests similarly to websites such as LeetCode~\cite{LEETCODE}, who host weekly and biweekly contests for their users to compete in for a similar purpose. Of course, there will also be some students who may be anxious at the idea that their performance would be public for all to see - for which this competitive feature can be optional for students to participate in.

\subsection{Frontend Technologies}

In order to utilise the World Wide Web that he had invented in 1990, Tim Berners-Lee had created WorldWideWeb, later Nexus~\cite{NEXUS}, the first web browser - which served as an inspiration for many subsequent browsers. These browsers were designed to load HyperText Markup Language (HTML) files, which later evolved into different web pages for consumer use as the Web had developed. Combined with Cascading Style Sheets (CSS) and JavaScript, they form the base framework used to create webpages ever since the dawn of the internet - with HTML files serving as the base, CSS files beautifying the styles, and JavaScript adding functionality to the webpages.

While it is possible to design a website solely with these three technologies, over time many different code libraries have emerged, bringing different controls and code reusability to web development. Ultimately, these libraries would be merged together and form a framework - with the intention of helping users create websites from start to end, as well as handling authentication, routing among other key features~\cite{FRAMEWORKS}. Two of the most popular JavaScript based frameworks include: Angular and React, though there are many others written in different programming languages.

% Angular
\textbf{Angular}\\
The original Angular (known as AngularJS) was created in 2009 as an open-source, client-side JavaScript framework promoting a high-productivity web development experience~\cite{BRANAS_ANGULAR}. The idea behind AngularJS was that developers would be able to simplify their code bases, as the framework was designed around the fact that components can be reusable and easily maintainable. In 2010 AngularJS was made open-source, allowing others to use the library to create their own applications. However, as JavaScript faced many improvements over the years that had followed, AngularJS was soon unable to meet requirements for large development projects, and ultimately became obsolete. As a result, Google created Angular 2 (otherwise known as Angular), which was released in 2016~\cite{ANGULAR_ANALYSIS}.

While AngularJS revolved around the MVC framework, Angular was designed to be a component-based framework. Each component is made up of HTML, CSS and TypeScript files, an example of which an be shown as:

\begin{lstlisting}[language=javascript, caption={An example of a "Hello World" component in Angular\cite{HELLO_ANGULAR}}]
	import { Component } from '@angular/core';
	
	@Component({
		selector: 'app-root',
		standalone: true,
		imports: [],
		template: `<h1>Hello world!</h1>`,
		styleUrls: ['./app.component.css'],
	})
	export class AppComponent {
		title = 'homes';
	}
\end{lstlisting}

Angular's use of TypeScript, as opposed to JavaScript, ensures that projects are statically typed — requiring developers to declare the types of variables, parameters, and return values at compile time, thereby reducing the likelihood of runtime errors. Additionally, TypeScript supports the use of interfaces, allowing custom types to be defined and reused across a project. Combined with Angular’s modular architecture — where logic can be split into separate files and imported as needed — this leads to improved maintainability and scalability in large codebases~\cite{TSvJS}.\\

% React
\textbf{React}\\
React was initially created in 2011 by Facebook and over time expanded as tools were subsequently released to further enhance the React library - ultimately making it into the comprehensive library that developers use today. React itself is used for creating the views for a web page, while a sister component ReactDOM is used to render the UI in the browser~\cite{BANKS_REACT}. More importantly, React utilises JSX - a hybrid of JavaScript and XML, which provides a simplified interface to create React components. An example of how a React component is defined with just JavaScript can be shown as:

\begin{lstlisting}[language=javascript, caption={An example of a React element being defined with JavaScript\cite{BANKS_REACT}}]
	function IngredientsList() {
		return React.createElement(
			"ul",
			{ className: "ingredients" },
			items.map((ingredient, i) =>
			React.createElement("li", { key: i }, ingredient)
			)
		);
	}
\end{lstlisting}

However when it comes to implementation with JSX, given the use of XML the syntax is comparable with HTML when it comes to developing a webpage, as seen in the following example:

\begin{lstlisting}[language=javascript, caption={An example of a React element being defined with JSX (IngredientsList and Ingredient are external functions)\cite{BANKS_REACT}}]
	<IngredientsList>
		<Ingredient />
		<Ingredient />
		<Ingredient />
	</IngredientsList>
\end{lstlisting}

Usage of JSX with React ultimately makes it easier to learn as a whole, as it combines very well with HTML elements to form the webpages required for the application. Components are also reusable, and ultimately makes React an ideal tool when it comes to Web Development.\\

When it comes to the differences between these two frameworks, Angular is known to have a steeper learning curve - given that it uses TypeScript as opposed to JavaScript, along with the extensive features that it provides. At the same time, React has an easier learning curve as it revolves around the idea of reusable components. Angular has a large community which has Google backing, while React offers extensive libraries and resources as a result of a significantly active community supporting it~\cite{FRAMEWORKS_COMPARE}.\\ 

However, for the frontend of this project, I will be using Next.js. Built on top of the React framework, Next.js is designed to address React's limitation when it comes to server-side rendering, whilst including many of its own additional features~\cite{DB_NEXTJS} such as better Search-Engine Optimisation and Routing, both of which would be required for the web application to gain traction in the future, as well as static site generation. Next.js also supports the use of TypeScript, bringing the previously mentioned advantages of static typing to the framework. This decision effectively combines the modularity and scalability of Angular with the flexibility and component-driven nature of React, offering a robust and efficient development environment for the frontend\\

Alongside Next.js, my project will be styled using TailwindCSS. Tailwind is a utility-first CSS framework, allowing developers to embed styles into their components as class names during development. During the build process, TailwindCSS scans all source files and converts the used class names into their corresponding styles before writing them to a minimal, optimised and static CSS file~\cite{TAILWIND}. This gives developers the ability to leave maintenance of separate CSS files to the framework, allowing them to focus more on component logic and maintain design consistency.

\subsection {Backend Technologies}

Similarly to the frontend, there are a number of backend frameworks in existence that are widely used for different web applications. These frameworks are designed to act as the core of any client-server based system, as they process majority of the application logic, and facilitate communication with database systems. Many of these frameworks are widely used, including - but not limited to Node.js and Spring Boot.\\

\textbf{Node.js}\\
Node.js was created in 2009 by Ryan Dahl, with inspiration from the V8 JavaScript engine seen in the Google Chrome web browser. It is an event-driven runtime environment designed to build scalable network applications. In Node.js, asynchronous callbacks are triggered for I/O operations, allowing the system to handle multiple concurrent connections efficiently. As a result, it's suitable for use with real-time applications that may require instant updates, such as chat applications~\cite{BACKEND_FRAMEWORKS_BLOG,BACKEND_FRAMEWORKS_REPORT}.\\ 

At the same time, given its single-threaded, non-blocking architecture, Node.js is widely used to develop REST APIs. This is achieved through the use of Express, which is the module that brings support for creating APIs to Node.js~\cite{NODE_API}. An example of a Node.js/Express endpoint can be shown below:

\begin{lstlisting}[language=javascript, caption={A basic GET endpoint that responds with a JSON object~\cite{NODE_API}}]
	import express from "express";

	const PORT = 3000;
	const app = express();

	app.get("/", (req, res) => res.json({status: "NTask API"}));

	app.listen(PORT, () => console.log(`NTask API - Port ${PORT}`));
\end{lstlisting}

With the models that Node.js follows, though they are ideal for some applications, for others that are more complex it can become increasingly difficult to manage the code. Alongside this, Node.js does not provide any native support for key security features such as password hashing or role-based access control. Instead, these must be manually configured using external libraries that can introduce additional complexity and maintenance overhead.\\

\textbf{Spring Boot}\\
Spring Boot was released in 2014 as a subproject under the Spring Framework, in order to simplify development of Java Web Applications.~\cite{MUSIB_SPRING} It uses a three-tiered architecture which include layers acting as Controllers, Services and Data Repositories - forming microservices as part of the overall backend system. Similarly to Node.js, Spring Boot can also be used to develop REST APIs for web applications, an example of which can be shown below:

\begin{lstlisting}[language=java, caption={A basic GET endpoint that responds with "Hello World!"}]
	@RestController
	@NoArgsConstructor
	@RequestMapping("/api")
	public class SpringController {
		@GetMapping("/hello")
		public ResponseEntity<String> helloWorld() {
			return ResponseEntity.ok("Hello World!");
		}
	}
\end{lstlisting}

Compared with Node.js however, Spring Boot includes many libraries that significantly enhance the security of web applications by providing built-in support for authentication and authorization, as well as protection against common vulnerabilities such as Cross-Site Request Forgery (CSRF) and Cross-Site Scripting (XSS). 

As an additional benefit, Spring Boot allows for seamless integration with database systems through the use of Hibernate, which uses the Java Persistence API (JPA) to map Java objects to database tables. This allows common operations to be abstracted into predefined repository methods, while still allowing developers to write custom queries for more complex data access requirements. As a result, I have chosen to use Spring Boot to power the backend of my project.

\subsection {Database Management Systems}

There are two major types of databases that are widely used across different applications, SQL and NoSQL. SQL (Structured Query Languages) have been the most popular form of storing data since the beginning of web application history, and this is largely due to the durability factor. This stems from the ACID properties that relational databases follow - which ensures that database transactions are full, and that data is kept intact and consistent. NoSQL databases on the other hand do not follow the idea of having a relational structure. These are typically customized to fit the needs of a particular application, and it is unlikely that one example of a NoSQL database can be used for many different types of applications~\cite{SQL_COMPARE}.\\

The biggest difference that NoSQL databases have in common is the use of BASE properties over ACID. BASE (Basically Available, Soft state with Eventual consistency) has been a critical discussion point when the two types of databases have been compared in the past - and are typically used in applications where inconsistent data can be tolerated~\cite{SQL}. This is not the case for my application - especially given that user details are required to be stored securely, so it is imperative that I make use of a database system that follows ACID properties.\\

There are still many databases to choose from that follow ACID properties. Two of the biggest database management systems include PostgreSQL and MySQL - which appear very similar on the surface however there are some key differences which make them stand out from each other. The biggest is that PostgreSQL is an Object-Relational Database Management System, providing the facilities of a standard Relational DBMS with additional Object Oriented concepts. This is beneficial for integration with Spring Boot, as it allows me to define entities that can be translated to database tables - making it possible to manipulate the system via the use of the Repository level in the backend such as in the following example. 

\begin{lstlisting}[language=java, caption={Similar functions are provided as built-ins.}]

\end{lstlisting}

\subsection{N-Tier Architecture}

The use of Spring Boot for the backend framework has allowed me to utilise an N-tier architecture, promoting modularity, scalability, as well as ease of maintenance. This is done by grouping the individual components into distinct layers: Controller, Service and Repository; each of which have their own roles when it comes to organising and structuring the codebase.\\

The \textbf{Controller layer} is used to receive the RestAPI endpoint request. This does not contain much logic - rather it instead acts as a protective layer to separate the external endpoint and the core application logic, as well as builds the final \verb|ResponseEntity| to be sent back to the frontend. \\

The \textbf{Service layer} is where the core application logic is kept. Given that it is not directly exposed to external sources, it is safer to handle business logic and processing requests here - as this is what will be accessing the repositories used to perform operations on the system's database.  \\

The \textbf{Repository layer} is used as the bridge between the backend and the database. Any entities that have been saved to the repository are translated into a record for the database table that the repository represents. At the same time, these repository classes can have different types of functions designed specifically to retrieve certain pieces of data from the database, to then use in the service layer.
\begin{center}
	\includegraphics[scale=0.75]{ntier.png}
	\captionof{figure}{N-tier architecture in Spring Boot, showing the data flow between layers.}
\end{center}

The workflow for this is as follows:
\begin{itemize}
	\item The Client makes the HTTP request that is received by the Controller.
	\item The Controller delegates the request to the appropriate method in the Service layer.
	\item The Service layer executes the business logic and interacts with the Repository to fetch or update data.
	\item The processed response is returned back through the Controller to the client.
\end{itemize}

\subsection{Client-Server Architecture}

Client/Server Architecture relates to the idea that two separate applications communicate with each other as part of a wider product. The Client would ask for and receive services that the Server would provide~\cite{CSA}. This is the case in my product, wherein the backend is responsible for managing any information that is to be stored and retrieved from the database, and the frontend requests this for for the end user to interact with.\\

Communication is facilitated through the use of API endpoints. These endpoints are URLs within a web application which point towards the different functionalities that an application provides. On the server side of the connection, the server would process the information required, whereas the requests for each function are called on the client side~\cite{API}.\\

An example of how this is setup in my application can be with how we view the list of qualifications that the user sees when they sign up to the application. When the create page is loaded, an API request is sent to the backend to fetch all of the qualification, the result of which will be stored as a constant to be used in the registration form itself.

\begin{lstlisting}[language=JavaScript, caption={When the page is loaded, axios sends an API request to get all the qualifications.}]

		const quals = async () => {
			const response = await axios.get("http://localhost:8080/api/qualification/get-all")
			return response.data;
		};
		
		quals().then(data => {
			setQualifications(data);
		})
	}, [])
\end{lstlisting}

\verb|localhost:8080| refers to the Spring Boot backend, while \verb|/api/qualification/get-all| refers to the specific endpoint mapped to the function that returns all of the qualifications in the system.

\subsection{Security Detail}

Being a web application that handles a user's private data, is is imperative that I secure the product, by minimising possible weaknesses that can be exploited. Out of all software available, the web browser is one that will run code provided from untrusted sources whenever presented\cite{WEB_SEC} despite being used to submit and receive private information across the world. With that in mind, it was important that I research adequate methods to protect the JSON Web Token that it used to prove the user's authenticity.\\

There are many ways that people may choose to store JWTs, be it in memory or even in the browser's session storage. However, research has shown that these are not as viable compared to the use of cookies. Storing the token in memory leaves the risk of it disappearing when the browser is closed or reset. On the other hand, storing it in Session Storage leaves the token vulnerable to Cross-Site Scripting (XSS) attacks. With cookies, by settings the HTTPOnly, Secure and SameSite flags to be true - there is added protection which prevents these cookies from ebing identified by external JavaScript, protecting them from XSS attacks~\cite{JWT}.

\includegraphics[scale=0.465]{cookies-outline}
\captionof{figure}{The HttpOnly and Secure flags are set to true, and the SameSite flag has been set to "Strict"}

This is not the only point of concern when it comes to security. It is also crucial to sanitise inputs as a means of removing any possible control characters - so as to not inject any malicious code into the system. This is a benefit of React, and therefore Next.JS, as all inputs are sanitised before being used within the frontend application. This is achieved by converting everything to a string before being rendered or used, adding further prevention to XSS attacks~\cite{XSS_REACT}. Where SQL injections are concerned, there are two types of queries that have been written for the backend. One type refers to the default functions that come with a JpaRepository, representing standard queries - while the other type relates to custom queries that I have had to write for the system. These custom queries are written with the use of named parameters, reducing the user's input only to valid arguments to complement them~\cite{SQL_PARAM}. The query is therefore built through the code, instead of being completed by the code.

\subsection{Privacy}

The United Kingdom has a General Data Protection Regulation Act that has been imposed to set out the legislation behind usage of personal data in a variety of applications. The following principles are set out in the act~\cite{GDPR}:

\section{Methodology}
There are many different approaches when it comes to Software Development. The Waterfall model for example focuses on completing phases of the project at a time, i.e. requirements first, then design and implementation etc. For me this approach is very strict - as it requires myself as the developer to consider the application as a whole from the very beginning, when the requirements of the product are continuously evolving as development ensues. Another example of a development approach can be Rapid Application Development. This approach focuses more on developing components in parallel to each other, prioritizing speed over completion of features. Though it closely aligns with my current development approach - it is also unsuitable as it requires components to be integrated to the system as a later date, as opposed to during the development process.\\

As a result, I have chosen to develop this application by following a combination of the Agile and Incremental Approaches. The Incremental Approach allows me to focus on developing one feature at a time - ensuring that it's working to the fullest before I move my focus onto the next feature in sequence. The Agile Approach here relates to the flexibility that I am giving myself; there is no dedicated client for this product, so I am able to develop features at my own pace and alternate between different features as I wish to. At the same time, I am then able to revisit features if I am required to make any additions following its completion - given the ongoing flexibility in requirements. This can be referred to as similar vertical slicing - wherein the application is developed component by component - and ultimately expands from these components as a dependency.

	// AuthController.java
	@PostMapping("/login")
	public ResponseEntity<String> authenticate(@RequestBody final AuthenticationRequestDto authenticationRequestDto) {
		try {
			AuthenticationResponseDto response = authenticationService.authenticate(authenticationRequestDto);
			ResponseCookie cookie = cookieService.createTokenCookie(response.accessToken());
			ResponseCookie cookieExpire = cookieService.createTimerCookie();
			return ResponseEntity.ok().header(HttpHeaders.SET_COOKIE, cookie.toString(), cookieExpire.toString()).body("User logged in successfully");
		} 
		// Error Handling
	}
\end{lstlisting}

The returned JSON Web Token is required for future API Requests, where the user needs to be authenticated for the functions to be executed. Additionally, a secondary cookie is returned with a timestamp that represents the time two minutes before the token is due to expire. This is used to trigger the refresh token mechanism - so that the token can be automatically refreshed if the user is within the two minute window. Both cookies have been designed to be as secure as possible. This includes setting the HTTP-Only and Secure flags to true, so that they are not detected by any external JavaScript - as well as ensuring that the sameSite flag is set to Strict. \subsection{Refresh Tokens}

The tokens used to verify the user's authenticity have been designed to expire after 15 minutes, for situations where the token is stolen by an attacker. However, users will want to utilise the system for a period longer than 15 minutes - so to accommodate I have introduced a Refresh Token system. This I have achieved with the introduction of middleware. 

The middleware will take the tokenExpiry cookie that was previously generated when the user logs in, as shown in Section 3.2. This cookie contains a timestamp that represents two minutes before the token cookie itself is due to expire. The middleware will check to see if the time is within those two minutes, and if that is the case it will send an API request to generate a new token. The token is generated and sent back to the middleware, where it's converted to a cookie and then sent with the original request response to the frontend.

\begin{lstlisting}[language=JavaScript, caption={If we have entered that expiry window, then the request is sent for a new token. The values are then unpacked and converted to cookies for the next response to the frontend.}]
	// middleware.ts
	const isExpired = checkExpiration(tokenExpiry);
	// time is up?
	if (isExpired) {
		console.log("Token Expired!")
		const token = req.cookies.get("token")?.value;
		await axios.post('http://localhost:8080/api/refresh/refresh-token', {},{
			headers: {
				'Cookie': `token=${token}`,
				
			},
			withCredentials: true}).then((resp) => {
			// Apply new values to the cookies
			const newToken = resp.data.token;
			const newExpiry = resp.data.tokenExpiry;
			// Calculate cookie expiry time
			const cookieExpiry = Number(newExpiry) + 120;
			const newExpiryDate = new Date(0).setUTCSeconds(cookieExpiry);
			// Apply to new cookies
			response.cookies.set("token", newToken, {expires:newExpiryDate, httpOnly:true, secure:true, sameSite:"strict"});
			response.cookies.set("tokenExpiry", newExpiry, {expires:newExpiryDate, httpOnly:true, secure:true, sameSite:"strict"});
			console.log("Token Refreshed!");
		});
	}
\end{lstlisting}
In the backend, the API request will gets the user from the database and check to see if they have a valid refresh token. It is unlikely that they won't have one - given that a valid one would generate when they log in should one be expired - however if this is not the case then they would have a new one generated. After this, with the refresh token confirmed - a new JWT is generated using the user's username as the payload.
\begin{lstlisting}[language=Java, caption={The backend checks if the token is valid, before generating a new JWT}]
	// RefreshTokenService.java
	public AuthenticationResponseDto refreshToken(String accessToken) {
		User user = userService.getUserByUsername(jwtService.extractUsernameFromToken(accessToken));
		// Checks expiry data is valid.
		if (hasInvalidRefreshToken(user))
		// No token found? Somehow? Brand new one then
		createToken(user);
		
		final var newAccessToken = jwtService.generateToken(user.getUsername());
		return new AuthenticationResponseDto(newAccessToken);
	}
\end{lstlisting}

	public AuthenticationResponseDto authenticate(final AuthenticationRequestDto request) throws AdminException {
        final var authToken = UsernamePasswordAuthenticationToken.unauthenticated(request.username(), request.password());
        final var authentication = authenticationManager.authenticate(authToken);

        final var accessToken = jwtService.generateToken((JpaUserDetails) authentication.getPrincipal());

        }

        return new AuthenticationResponseDto(accessToken);

        log.setDate(Instant.now());
        logRepository.save(log);
    }
\end{lstlisting}

All logs are then presented on the main admin dashboard as previously mentioned. Here the admin can scroll through the list to see who performed a specific action, where the logs are sorted from the latest date to oldest.

\chapter{Professional Issues}

Professional Issues occur wherever computing meets society. As such they are always concerned with how people interact with computers and software. This is a very wide area and you may well choose a topic not listed below but these are given as guidelines to help you. \url {https://moodle.royalholloway.ac.uk/mod/page/view.php?id=744455}
\begin{itemize}
\item Usability - accessibility, replacing humans, artificial intelligence.

\item Plagiarism - correct citation, using code with acknowledgement.

\item Licensing - shareware, open source, copyright, patenting, reverse engineering.

\item Safety - reliability, economic impact, trust, provided "as is" clauses.

\item Privacy - web privacy, legal issues, data usage.

\item Monopoly - proprietary formats, tie-ins, cartels, DRM, Google, Amazon, Microsoft, Apple.

\item Management - appropriate costing of time and resources at the start of a project. Revision during project. Consultation with stakeholders.
\end{itemize}
